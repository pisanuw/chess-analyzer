## Purpose

Help a FIDE ~2000 player (Yusuf's son) improve: the engine finds the critical moments, the model explains them and classifies the error, and the classifications accumulate into a weakness profile plus drills from his own games. See README.md for the feature list.

## Decisions

- Local app, `claude` CLI for explanations (no API key, no per-token cost). Frontend kept static so a hosted Netlify build with Stockfish WASM plus an API-key client can be added later without rewriting views.
- Vanilla JS, no build step. chessground for the board, chess.js for rules, hand-rolled SVG charts.
- Error categories (fixed enum in `server/prompts.js`): tactics-allowed, tactics-missed, calculation, positional, opening, endgame-technique, conversion, defence. Time pressure is a separate boolean, not a category.
- Pattern names are free text but the prompt lists the player's existing pattern names so the model reuses them; the report aggregates by normalised name.
- Critical moment threshold default 12 win-probability points (between inaccuracy and mistake). Drill threshold 20.
- Puzzles are derived on demand from the analysed game files (`server/puzzles.js`, `GET /api/puzzles`), with no store and no sync step: they update the instant analysis finishes and need no LLM. Drills, by contrast, are a persisted per-machine store synced after analysis and again after explanation. Keep puzzles stateless (that is what keeps them working on the read-only mirror).
- Local server entry point is `server/serve.js` (owns `listen` and boot housekeeping). `server/index.js` only builds and exports `app`, so tests and the Netlify function can import it without a listener or `import.meta`. Do not add `import.meta` to anything in the function's import graph: the esbuild CJS bundle leaves it empty and warns.
- Opponents key on FIDE id, not name (`data/players.json`, synced small reference data). Ids come free from PGN tags (`WhiteFideId`/`BlackFideId`) and book-export filenames; anything else is resolved by an explicit, confirm-each-match FIDE lookup (`server/fide.js`, ratings.fide.com), never an automatic scrape at import (keeps the local-first principle: only the claude CLI and this deliberate lookup leave the machine).

## Known limitations

- One engine process per role (analysis, sparring/quick evals), one job at a time. Fine for a few games per week.
- Phase classification is a material/move-number heuristic (`phaseOf` in analyze.js).
- Drill correctness is "engine best or within 3 win-probability points"; no tablebase check for endgames (play-out drills soften this for conversion/defence).
- The manual LLM flow works but is clunky (copy prompt, paste JSON), and manual mode has no batch or re-explain.
- No lichess/chess.com import yet (public APIs, no auth needed; was descoped for v1). Opponent games now come from FIDE-named per-player exports (the scout book tier); online-username import is still open.
- Scout books: FIDE id comes from the export filename (games carry no FIDE tags), and the subject's side is found by exact name match, so an opponent whose name is spelled differently across files needs an alias. The book's PGN blob is stored per opponent, so `data/scouts/` grows (now excluded from the data repo via `ensureDataIgnores`). The 739-game parse is synchronous (~5s) and blocks the event loop for that one import.
- No unlink/replace for a FIDE-id link: re-linking a name to a second id makes it ambiguous (`lookupFideId` returns null), so correcting a wrong link means editing `data/players.json` by hand. Three homonym opponents (Liu Austin, Xiong Michael, Kwiatkowski Maciej) are unlinked pending a manual pick.
- Decoy selection is heuristic (judgment best, 10+ win-prob spread in the stored lines, ply > 10); tune ratios and criteria from use.
