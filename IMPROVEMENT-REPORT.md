# Improvement report: frontend, backend, opponent-preparation pedagogy

Findings from a read-only review of the current codebase (no build-step/framework changes proposed; `public/api.js` stays the only frontend-backend boundary; no API-key LLM provider proposed). Ordered by section, roughly most valuable first within each. File/line references are approximate and will drift as the code changes.

## Frontend

1. **Duplicated engine-lines markup.** The `<ul class="lines">` eval-chip/SAN/"best"-or-"played" block is copy-pasted in `public/views/game.js`, `public/views/drills.js` (three places), and `public/views/prep.js`. Extract a `linesList(lines, playedUci)` helper into `widgets.js` so future formatting changes (e.g. click-through to a move) are one edit instead of five.
2. **Whoami menu has no ARIA menu semantics.** `public/app.js` toggles `#whoami-menu`'s `hidden` class on click/outside-click; the trigger never gets `aria-expanded`/`aria-haspopup`, the menu isn't `role="menu"`, Escape doesn't close it, and focus never returns to the trigger on close.
3. **Modal overlays have no focus trap.** `pickPromotion` (`public/board.js`) sets no initial focus at all, and `editNamesDialog` (`public/views/game.js`) focuses the first input but doesn't trap Tab inside the dialog or restore focus to the opener on close.
4. **Current nav item isn't exposed to assistive tech.** `public/app.js` toggles only a CSS `.active` class on the matching `[data-nav]` link; add `aria-current="page"` so screen-reader users can tell which page is current.
5. **No landscape-phone breakpoint for board layouts.** `.game-layout` and `.drill-layout` in `style.css` collapse to one column below 900px with no separate treatment for the ~700-850px landscape-phone range, which is the realistic tournament-hall orientation: the player scrolls past the board to reach guess/grade buttons after every move.
6. **Chart resize redraws are undebounced.** `observeWidth` in `public/charts.js` rebuilds the whole SVG on every ResizeObserver tick past an 8px threshold, with no `requestAnimationFrame`/debounce; a dragged window edge or a flipping accordion can trigger many full redraws per second.
7. **Offline failures get silently downgraded to "empty" inside some views.** `api.js` already tags network failures with `err.offline` so the router can show a distinct "Cannot reach the server" state, but `scout.js` (`api.scout(...).catch(() => null)`, `api.games().catch(() => ({games: []}))`) and `games.js` (`api.members().catch(...)`) swallow that signal locally, rendering "nothing to show" instead of an offline message.
8. **`pollClash` in `scout.js` outlives the view.** It polls `api.jobs()` every 1.5s for up to 5 minutes while an opponent's clash tree builds; the view's `destroy()` only tears down the chessboard, so navigating away mid-build leaves it polling and eventually rendering into a detached container. Route it through `app.js`'s existing nav-token/cancellation pattern.
9. **No responsive, offline, or drag-interaction coverage in the smoke test.** `test/ui/smoke.mjs` uses a single fixed 1200x900 viewport; none of the CSS breakpoints, touch/drag board interaction, or the offline review queue are exercised.
10. **Several high-risk interactive flows are untested even at the smoke level:** PGN import, "Guess the move"/"Guess their move", "Play it out", drill suspend/undo and the conversion/defence playout drills, and the opening-clash controls (extend-with-engine, narrate, tree/lichess toggle).

## Backend

1. **Job queue is one global FIFO across all members and job kinds.** `server/jobs.js` processes analyse, explain, and clash jobs in strict arrival order; one member's large scout-book promote can starve every other member's work for a long stretch. Two lanes (interactive own-game work vs. bulk scout/clash work) would be cheap and wouldn't require a scheduler rewrite.
2. **`.tmp` sweep isn't recursive.** `sweepTmpFiles` in `server/store.js` only cleans `DATA_DIR` and `GAMES_DIR`; a crash mid-write can leave orphaned `.tmp` files under `data/scouts/`, `data/users/<id>/`, and other subdirectories forever.
3. **Game listing rescans the whole flat directory every call.** `listGames`/`listAllGames` `readdir` + `stat` every file in `GAMES_DIR` on each request; the parsed-game cache skips re-parsing but not the directory scan, so per-request cost grows with total games across all members, not per-user. A small persisted index (or per-owner subdirectories) would make the common per-user list O(1).
4. **Synchronous PGN parsing blocks the event loop.** `routes/games.js` parses an import of up to 500 games synchronously in the request handler, same class of issue already tracked for the 739-game scout-book parse but not yet mitigated for ordinary imports. Yielding via `setImmediate` between chunks would help both paths.
5. **One shared rate-limit bucket across unrelated auth-adjacent actions.** `auth.js`'s per-IP bucket (20/hour) is reused for password login, magic-link requests (`magiclink.js`), and prep-sheet email requests (`routes/scout.js`); heavy legitimate use of one can lock out another from the same IP (a shared office network). Give each action class its own counter.
6. **Admin "viewing as" leaves no audit trail.** `requireAdmin` only logs non-GET requests, so an admin browsing another member's private report/games via `?user=` is never recorded in `server/audit.js`. Log impersonation explicitly, separate from routine admin GET traffic.
7. **Uncaught errors return raw `err.message` to the client.** `http.js`'s `wrap()` forwards internal error text (e.g. raw `fs`/store error strings with paths) straight to the HTTP response. Return a generic message for 5xx and keep the detail in the server log only.
8. **Retry coverage is inconsistent for LLM calls.** Only the batch/explain job path wraps `complete()` in `completeRetry`; direct call sites (re-explain, prep-sheet generation, clash narration) call `complete()` directly, so a single transient `claude` CLI hiccup fails the whole interactive request. Route every call site through the shared retry helper.
9. **Thin test coverage on two foundational modules.** `server/engine.js` (UCI line parsing, command queueing/timeout) and `server/llm.js` (CLI JSON/error parsing) have no direct unit tests, only indirect coverage via `enginepool.test.js`/`jobs.test.js`; a stdout-parsing regression could slip through CI. `server/memo.js`'s LRU eviction (used by every report/repertoire cache) is also untested.
10. **Two files have outgrown a single responsibility.** `server/drills.js` (~650 lines) mixes ease/interval math, drill-object construction, decoy selection, store-mutation locking, and review CRUD; `server/clash.js` (~500 lines) mixes book-index building, forest assembly, engine-leaf extension, and narration keys. Splitting the ease math and decoy heuristic out of `drills.js` (both already flagged in BRIEFING.md as needing tuning from use) would let them be iterated without touching locking logic; splitting index-building from forest assembly in `clash.js` would make the trickiest part independently testable, in the spirit of the existing `server/routes/*` split.

## Pedagogical: preparing for a specific opponent

1. **Predicted lines aren't Elo-banded, so a changed opponent can mislead.** `scoutDossier`'s engine-analysis subset filters to games within Elo of the opponent's *current* rating, but the Opening Clash index and book repertoire shares weight purely by recency (server/clash.js explicitly notes "no Elo-band filter here"). A predicted line can be dominated by games from a materially different version of the opponent. Apply the same Elo-band filter (or a rating-trend-aware weight) to the clash index and repertoire shares, not just the engine-analysis subset.
2. **The opponent's rating trend is computed but never reaches the coach model.** `eloTrend` is returned by `scoutDossier` and passed into `book`, but `prepContext` (server/prompts.js) only cites current/peak Elo and results. A fast-rising junior and a plateaued veteran at the same current rating get identically-worded advice. Cite the trend explicitly as its own evidence item so the sheet can flag "their history is less predictive than usual."
3. **Sparring matches the opponent's rating, not their style.** `startSparring` (public/views/prep.js) sets engine strength to the opponent's current Elo only; it never biases toward documented tendencies (poor conversion, time trouble, weak defence) from `tendencies.js`. Practicing predicted middlegames trains against "someone your opponent's rating," not "someone who collapses under pressure the way they do." When a position falls in a category the opponent is weak in, bias the sparring engine's play (or at least surface the relevant tendency next to the play-out).
4. **No middlegame/structural plan beyond the opening tree.** `featureCollector` (server/clash.js) derives real structural habits (castling side, opposite-side-castling rate, queen-trade timing), but the prep-sheet's `exploit_plan` field is 2-5 generic sentences with no requirement to translate a structural habit into a concrete plan ("they castle opposite sides 40% of the time as White; race the queenside pawns"). Add a "typical structures and plans" section to `PREP_SHEET_SCHEMA` that must cite those habit ids.
5. **Early deviations get no rehearsal.** `sparringPositions` (server/prep.js) only keeps clash leaves with path length >= 4 plies, so a likely move-2/3 surprise from a "new" opponent, arguably the highest-risk moment against someone you haven't played, has no drill or play-out. Add a shallower "if they deviate immediately" sparring bucket from the root position.
6. **No must-win-vs-safe-draw branching.** The tool has no notion of tournament context. `exploit_plan`/`openings` are identical regardless of whether the student needs to complicate or simplify, even though the signals to support that (opponent's score in balanced/out-of-book positions, hold rate) already exist in `tendencies.js`. A "need: win/draw/either" flag on the Prepare page could reweight which lines and plan steps the sheet emphasizes.
7. **The student's own weaknesses are never crossed with the opponent's strengths.** `prepContext`'s student block (server/prompts.js) is rating and opening lines only; it never pulls the student's own weakness categories from their personal report, so a real risk like "you convert poorly in rook endgames and they specifically steer there" never surfaces. Feed the student's own category/phase weaknesses into `prepContext` and ask explicitly for a "matchup risk" callout.
8. **Clock behavior is reduced to blunder counts, not a pacing curve.** `report.timeManagement` gives only blunder-under-time-pressure counts; there's no "typically under 10 minutes by move 30" curve, even though the book PGNs likely carry `%clk`. A median-clock-by-move-number tendency would let the student plan to steer toward a long grind or a sharp tactical shot based on when the opponent actually runs short.
9. **Post-game learning doesn't compound toward a rematch.** `walkPrediction`/the head-to-head hit rate report where a prediction left the tree, but nothing distinguishes a one-off deviation from a repeated pattern across multiple games against the same opponent. Surface repeated deviations across the head-to-head record as their own evidence item feeding the *next* prep sheet's watch-list.

## Suggested next steps

Given the existing "route split" and "shared helpers" precedent in this codebase, the cheapest, highest-leverage items to pick up first are: the offline-signal fix and `pollClash` cleanup on the frontend (both are correctness bugs, not polish); the LLM retry consistency and admin-impersonation audit gap on the backend (both are one-function fixes); and the Elo-band filter on the clash index plus citing `eloTrend` in the prep-sheet prompt (both reuse data the code already computes) on the pedagogical side.
